# Event Planner Mini

This project demonstrates practical use of data structures:
linked lists, stacks, queues, maps, trees, sorting, and searching.

# **Required Data Structures and Why They Were Used**

## GuestListManager

### **LinkedList - Guest Storage**
- Used to store the full list of guests in the order they were added.
- Supports fast insertions and removals.
- Matches the assignment requirement to use a linked list as the “source of truth” for the guest list.

### **HashMap — Guest Lookup**
- `Map<String, Guest> guestByName` enables O(1) average‑time lookup by guest name.
- Required for fast searching and removal.
- Ensures consistency between the list and the lookup table.

## SeatingPlanner

### **BST (TreeMap) — Grouping Guests for Seating**
- `TreeMap<String, Queue<Guest>> groups` automatically sorts group tags using a **Red‑Black Tree** (a self‑balancing BST).
- Satisfies the assignment requirement to use a **Binary Search Tree** for ordered seating.
- Ensures groups are processed in sorted order when generating the seating chart.

### **Queue — Ordering Guests Within a Group**
- Each group stores guests in a `Queue<Guest>` (LinkedList).
- Preserves FIFO order so guests are seated in the order they were added.

### **Map — Table Assignments**
- `Map<Integer, List<Guest>> tables` stores the final seating chart.
- Keys are table numbers; values are lists of guests.
- Efficient for random access and modification.

## VenueSelector

### **BST (TreeSet) — Venue Selection**
- VenueSelector uses a `TreeSet<Venue>` with a custom comparator.
- Automatically sorts venues by:
    - lowest cost
    - then smallest capacity
- Satisfies the assignment requirement to use a sorting algorithm or BST for venue selection.

### **Deque (Queue + Stack) — Task Management**
- `upcoming` tasks use queue behavior (FIFO).
- `completed` tasks use stack behavior (LIFO) for undo.
- Matches assignment requirement to use both a queue and a stack.

# **Sorting and Searching Algorithms Used**

### **Sorting**
- **TreeMap** and **TreeSet** both use **Red‑Black Trees**, which maintain sorted order with:
    - O(log n) insertion
    - O(log n) lookup
    - O(n) in‑order traversal
- Used for:
    - Sorting guest groups alphabetically
    - Sorting venues by cost/capacity

### **Searching**
- **HashMap lookup** for guests by name → O(1) average case
- **TreeSet** search for best venue → O(log n)
- **TreeMap** lookup for group queues → O(log n)

# **Big‑O Complexity**

### **1. Finding a Guest by Name**
Operation: `guestByName.get(name)`
- **Time Complexity:** **O(1)** average
- HashMap provides constant‑time lookup using hashing.

---

### **2. Selecting a Venue**
Steps:
1. Filter venues by capacity and budget → O(n)
2. Insert valid venues into a TreeSet → O(k log k), where k ≤ n
3. Retrieve the first (best) venue → O(1)

**Total Complexity:**  
\[ O(n + k \log k) \]  
Since k is typically much smaller than n, this is effectively **O(n log n)** in the worst case.

---

### **3. Generating Seating Chart**
Steps:
1. Group guests into a TreeMap → O(n log g), where g = number of groups
2. Iterate through groups in sorted order → O(g)
3. Seat guests into tables → O(n)

**Total Complexity:**  
\[
O(n \log g + n)
\]  
Since g ≪ n in most cases, this simplifies to **O(n)** for practical purposes.
